## Root Cause Analysis

### A: Kramdown IAL not parsed (3 pages, HIGH IMPACT)

Pages: `index.html`, `courses/index.html`, `courses/ml-zoomcamp/index.html`

Kramdown Inline Attribute Lists (IAL) like `{: .fs-9 }` and `{: .fs-6 .fw-300 }` appear as literal text in the HTML output instead of being applied as CSS classes to the preceding element. This is a core markdown processing feature of kramdown.

How it works in Jekyll/kramdown:
- `# Heading\n{: .fs-9 }` produces `<h1 class="fs-9">Heading</h1>`
- `Some text\n{: .fs-6 .fw-300 }` produces `<p class="fs-6 fw-300">Some text</p>`
- `[Link](url){: .btn .fs-5 }` produces `<a href="url" class="btn fs-5">Link</a>`

What rustkyll currently produces:
- `# Heading\n{: .fs-9 }` produces `<h1>Heading</h1>\n<p>{: .fs-9 }</p>` (literal text)

The IAL syntax supports: `.class-name` (CSS class), `#id-name` (HTML id), and `key="value"` (arbitrary attributes). For this issue, only class and id attributes are required, since those are what the DTC/docs site uses.

Source files affected:
- `websites/DataTalksClub/docs/index.md` -- uses `{: .fs-9 }`, `{: .fs-6 .fw-300 }`, `{: .btn .fs-5 .mb-4 .mb-md-0 }`
- `websites/DataTalksClub/docs/courses/index.md` -- uses `{: .fs-9 }`, `{: .fs-6 .fw-300 }`
- `websites/DataTalksClub/docs/courses/ml-zoomcamp/index.md` -- uses `{: .fs-9 }`

### B: Parent pages missing auto-generated child page listing (8 pages, HIGH IMPACT)

Pages: `activities/index.html`, `courses/course-management-platform/index.html`, `courses/data-engineering-zoomcamp/index.html`, `courses/data-engineering-zoomcamp/logistics/index.html`, `courses/data-engineering-zoomcamp/resources/index.html`, `general/guidelines/index.html`, `general/index.html`, `general/jobs/index.html`

The just-the-docs theme auto-generates a "Table of contents" section at the bottom of parent pages. This section contains:

2. `<h2 class="text-delta">Table of contents</h2>` (from `_includes/toc_heading_custom.html`)

The fix should ensure the `children_nav.html` include executes correctly to produce the child page listing. This is a Liquid template execution issue, not a Rust code generation issue -- the template already exists in the site's `_includes/`.

## Implementation Notes

### Fix A (Kramdown IAL)

The IAL parsing should happen during markdown-to-HTML conversion, likely as a post-processing step on the HTML output or as preprocessing of the markdown input. Two approaches:

**Approach 1 (Recommended): Markdown preprocessing** -- Before passing markdown to the parser, scan for `{: ... }` lines and transform them. For block-level IAL (on its own line after a block element), remove the IAL line and attach the attributes to the preceding element in the HTML output. For inline IAL (immediately after an inline element like a link), attach to the inline element.

**Approach 2: HTML post-processing** -- After markdown-to-HTML conversion, find leftover `{: ... }` text nodes and apply their attributes to the preceding HTML element.

The implementation must handle:
- Block IAL: `{: .class }` on its own line after a heading, paragraph, etc.
- Inline IAL: `[text](url){: .class }` immediately after an inline element
- Multiple attributes: `{: .class1 .class2 #id }`
- IAL must be stripped from the visible output

### Fix B (Child page listing)

The `children_nav.html` include uses several advanced Liquid features:
- `include_cached` -- rustkyll should treat this as `include` (or have a working cache)
- `group_by` on `parent` field
- `where_exp` filtering
- Complex string splitting of rendered nav HTML

If the template cannot be made to execute correctly with reasonable effort, an alternative is to implement child page listing as a generator-level feature that injects the `<hr>`, `<h2>`, and `<ul>` HTML directly when `has_children: true` and `has_toc != false`.

### Fix C (JSON-LD entity encoding)

In `src/template/seo_tag.rs`, HTML-entity-encode `&` as `&amp;` in JSON-LD string values before inserting into the `<script>` tag.

### Fix D (Fenced code block wrapper class)

In `src/kramdown.rs` around line 1782, change the no-language fenced code block wrapper from `class="highlighter-rouge"` to `class="highlighter-rouge language-plaintext"`. Update the existing tests that assert the old behavior.
