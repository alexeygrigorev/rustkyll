# Issue 75: Fix raw Liquid tags in feed.xml content

## Problem

Discovered in issue #63 feed/sitemap validation: the DTC feed.xml contains raw Liquid tags (`{{`, `{%`) in entry content. The feed structure is correct (20 entries, valid Atom XML, correct titles/dates/links), but the `<content>` or `<summary>` elements contain unrendered Liquid template syntax.

## Root Cause Analysis

The pipeline stores `html_content` on each `CollectionItem` during collection loading (`src/collection.rs` line 468) by calling `markdown_to_html(&doc.content)`. This converts markdown to HTML but does NOT render Liquid tags first.

When generating HTML page files, the generator (`src/generator.rs` ~line 595) correctly runs the Liquid+markdown pipeline for posts via `render_markdown_page_with_cached_site`. However, this rendered output is written directly to disk and is NOT stored back into `item.html_content`.

Later, when the feed is generated (`src/main.rs` line 371-372), `feed::write_atom_feed` receives the original `CollectionItem` structs whose `html_content` still contains un-rendered Liquid tags from the initial markdown-to-HTML conversion.

Posts that contain Liquid tags in their markdown body (e.g., `{% include %}`, `{{ site.url }}`) will therefore leak raw Liquid syntax into the feed output.

## Evidence

From `docs/comparison/feed-sitemap-results.md`:
- DTC feed.xml: 20 entries with valid structure
- Raw Liquid tags found in feed content (test `test_dtc_feed_validation` fails on Liquid tag check)

Known DTC posts with Liquid tags in content:
- `_posts/2020-12-07-practical-guide-better-code.md` (4 Liquid tags)
- `_posts/2023-08-17-machine-learning-zoomcamp.md` (3 Liquid tags)
- Multiple other posts with `{% include %}` and `{{ ... }}` tags

## Scope

This issue covers ONLY the programmatic Atom feed (`feed.xml`) generated by `src/feed.rs`. The kids podcast.xml Liquid template issue is tracked separately in issue #76.

The fix should ensure that the `html_content` used by the feed generator has been fully rendered through the Liquid engine. Possible approaches:
1. Update `html_content` on each `CollectionItem` after Liquid rendering in the generator, before the feed is generated.
2. Re-render post content through the Liquid engine in the feed generator itself.
3. Read the already-generated HTML page files and extract the body content for the feed.

The chosen approach must be generic (no site-specific hardcoding) and work for any Jekyll site that has Liquid tags in post content.

### [SWE] 2026-03-14 (PM rejection fix)
- Root cause found: The `render_markdown_content_with_cached_site` call used `item.front_matter` directly, but did NOT inject `url` or `date` into the page context. The `related-posts.html` include template does `{% assign current_post = page %}` then `{% if post.url != current_post.url %}`, which requires `page.url`. Without `url` in the front matter, the Liquid engine raised "Unknown index" (variable=current_post, requested index=url).
- The generator (`src/generator.rs` lines 553-568) injects `url`, `date`, `previous`, `next`, and config defaults into `page_fm` before rendering. The feed re-rendering was missing this step.
- Fix: Before calling `render_markdown_content_with_cached_site`, clone `item.front_matter` and inject `url` and `date` (matching what the generator does). This ensures `page.url` and `page.date` are available to Liquid templates.
- Also added: `eprintln!` warning on render failure so errors are visible instead of being silently swallowed.
- Also added: `strip_liquid_tags()` fallback function -- if Liquid rendering fails for any other reason, raw tags are stripped from `html_content` before writing to the feed (belt-and-suspenders approach).
- Verified: `_site/feed.xml` now has zero raw Liquid tags (`{%`, `%}`, `{{`, `}}`).
